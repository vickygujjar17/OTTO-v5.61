562: fix — flip the ENTRY_FRONT_EDGE entry from far-edge breakout chase to near-edge pullback trap

The v5.57 "front-running anticipation" entry armed the order 0.5*ATR BEYOND the
far edge the breakout crosses, so every setup was a STOP that chased extension:
a Resistance LONG at b.bottom+slDist (= b.top+0.5*ATR) and a Support SHORT at
b.top-slDist (= b.bottom-0.5*ATR). This change moves the entry to the EDGE THE
ARMING CLOSE HAS ALREADY CLEARED -- a LIMIT that waits for a retrace INTO the
level and traps the pullback, rather than paying up for the break.

ENTRY GEOMETRY (COttoOrderManager.mqh, COttoBlockManager.mqh)

  Both twins of the entry arithmetic flip together. They MUST stay
  byte-identical: COttoBlockManager::BlockEntryPrice() feeds the Front-Run veto
  projection while COttoOrderManager::CalcEntryPrice() feeds the order, so any
  divergence would have the veto judging a price the order never had.

    CalcEntryPrice()      LONG : block.bottom + slDist  ->  block.bottom - slDist
                          SHORT: block.top    - slDist  ->  block.top    + slDist

    BlockEntryPrice()     LONG : b.bottom + slDist      ->  b.bottom - slDist
                          SHORT: b.top    - slDist      ->  b.top    + slDist

  slDist is unchanged at blockHeight + 0.5*ATR, and the SL stays entry -/+
  slDist, so the RISK DISTANCE is identical on both sides of this change -- only
  the SIDE OF THE ZONE the order waits on moved. The waiting depth is one whole
  zone height plus half an ATR outside the near edge.


ROUTING: PHYSICAL REST IS ORDINARY AGAIN (COttoOrderManager.mqh)

  No router code changed, and none needed to: the Hybrid Router's priceValid
  test is a LIMIT-side legality test (BUY_LIMIT below bid, SELL_LIMIT above
  ask). Under the far-edge entry that test was false on the ordinary path, so
  the VIRTUAL arm carried every setup. Under the near-edge entry it is TRUE on
  the ordinary path, so a real broker limit now rests and the virtual arm drops
  back to its designed role: the fallback for a price that has already traded
  through the level, or a send the venue refuses. The virtual engine is retained
  in full -- arm book, cross test, MARKET fire, localTP re-derivation.

TARGET ANCHOR: DELIBERATELY UNCHANGED (COttoOrderManager.mqh,
COttoBlockManager.mqh)

  block.localTP stays anchored on the FAR edge (farEdge +/- tpRR*slDist) in all
  three places that derive it -- PlaceOrArmOrder, CheckVirtualTriggers and both
  BlockManager veto passes. Anchoring the projection on the pullback entry
  instead would push the target out by the entry's offset and veto setups that
  were never front-runs.

  The realized reward therefore CHANGES the SIGN of its deviation, and this is
  the one behavioural consequence worth stating loudly:

    v5.57  RR = InpMaxRR - 0.5*ATR/slDist         (4.0 -> 3.5R, below input)
    v5.62  RR = InpMaxRR + 1 + blockHeight/slDist (4.0 -> 5.5R, above input)

  The entry now sits a whole slDist outside the near edge while the far-edge
  target is untouched, so the reward spans the entire zone plus 1R plus the
  far-edge projection. On the documented 1.0-high zone at ATR 2.0 with
  InpMaxRR 4.0 the realized RR is 5.5R. Intentional, and pinned by the probe so
  a future re-anchor has to be a deliberate act.

A. CHighTableAuditor.mqh - aggregate (basket-summed) bound
---------------------------------------------------------------
   The existing check is a PER-LEG abort: it compares the worst SINGLE
   position against RiskPercent * 1.50 and is structurally blind to four
   legs that are each individually legal yet sum to four times the
   intended exposure. Added a second, INDEPENDENT gate:

     double sumRiskPct = 0.0;              // beside peakRiskPct
     sumRiskPct += posRiskPct;             // inside the loop, after the
                                           // lossDist <= 0.0 guard

   Ceiling is CONFIG-PROOF, recomputed every audit from the live ladder:

     nominalStackPct    = RiskPercent + InpRiskT2Pct + InpRiskT3Pct + InpRiskT4Pct;
     maxRungPct         = MathMax(...);
     maxAllowedStackPct = MathMax(nominalStackPct, maxRungPct) * 1.50;

   At shipped defaults that is 2.75 * 1.50 = 4.125%, against a full-ladder
   2.75%. The gate is therefore INERT on the shipped config by design: it
   is a misconfiguration canary, not live-exposure protection. A heavier
   ladder lifts its own ceiling; a botched rung cannot outrun it.

   The peak gate is byte-identical and still evaluated first, so v5.46
   loss-side isolation is untouched (test_v546 28 -> 37 checks, 0 fail).

   Two-phase confirm: one audit cycle can catch the basket mid-scale-in
   before a fresh rung has its SL written, so the first breach only sets
   m_aggRiskSeen and the alert dispatches on the SECOND consecutive cycle.
   Healthy path re-arms BOTH the latch and the confirm flag.

   New members (declared inside the include guard, initialised in the ctor):
     bool m_alertSent_AggRiskBreach;  // trailing // comment is required by
                                      // test_v532_hightable.py:247 regex
     bool m_aggRiskSeen;
